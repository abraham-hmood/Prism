--------------------------------------------------------------------------------
ARCHITECTURE RULES (apply to every phase)
--------------------------------------------------------------------------------

  * :core is a plain Kotlin/JVM module. android.jar is NOT on its classpath.
    An "import android.*" in :core is a compile error, by design. Never add the
    Android plugin to :core to make something compile.
  * Platform differences go behind CAPABILITY interfaces in com.prism.core,
    defined by what Prism NEEDS, not by what Android offers. Do not create
    IPackageManager / IContext / IBitmap. See AppCatalog and PlatformHost for
    the pattern that is already established.
  * Persistence keys and store names MUST NOT CHANGE when moving code to :core.
    Existing Android installs read those exact strings. Changing one silently
    resets a user. See NoraConfig.loadGeometry for the migration pattern.
  * Every platform adapter should be THIN. If an adapter grows logic, the
    interface asked for a mechanism instead of a capability — redesign it.
  * Android must keep working after every phase. This is one product, not a
    fork.

--------------------------------------------------------------------------------
WHAT HAS NO DESKTOP EQUIVALENT (do not pretend otherwise)
--------------------------------------------------------------------------------

  * SMS / MMS — Windows has no public API, Linux needs a cellular modem.
    Desktop Messages is AI-only. Phase 40 covers relaying SMS from the phone
    over the mesh instead, which is the real answer.
  * Android Virtualization Framework (android.system.virtualmachine) — booting
    a whole guest OS. Desktop uses QEMU/libvirt for THAT, and it is a
    REIMPLEMENTATION rather than a port. This is about running an OS in a VM and
    is not the same thing as running an Android APP (see PHASE 111, which is a
    port and is NOT to be done with an emulator).
  * LocalOnlyHotspot / WifiP2p — Windows netsh, Linux nmcli/hostapd. Also a
    reimplementation.
  * ShakeDetector — no desktop analogue. Rebind to a hotkey.

[x] PHASE 6 — Replace org.json with kotlinx.serialization
    Source: AgenticWireFormats, AgenticEngine, PrismMeshService, P2pDnsManager,
            P2pModelRegistry, CloudAiService, NebulaSocialManager,
            ModelDiscoveryService, AccessPointModel (toJson x4)
    org.json is Android-only. NoraFeedback KEEPS its hand-rolled parser — it
    exists to preserve an exact on-disk format, do not "unify" it away.
    Done when: no org.json import remains outside :app UI code.

    DONE 2026-08-04. Zero org.json references remain anywhere, including the
    UI code the criterion allowed to keep them.

    NOT converted to @Serializable data classes, and that was the whole
    decision. 196 JSONObject/JSONArray references across 20 files, and those
    objects ARE the wire format -- mesh gossip, DNS records, the model
    registry, agentic tool-calling, cloud AI request bodies. Twenty separate
    hand-conversions means twenty separate chances to change a payload
    subtly, and the failure lands on a peer's machine or a third-party API,
    not here. So core/json/Json.kt reimplements org.json's API on
    kotlinx.serialization and the call sites changed only their import.
    NoraFeedback's parser untouched, as instructed.

    One real incompatibility, worth knowing if this pattern is reused:
    org.json's optString(key, fallback) types its fallback as a Java platform
    type, so optString("ip", null) compiles there. The portable one types it
    non-null so the other 31 call sites keep returning String. Fixed at the
    single call site (DiscoveryEngine) with explicit isNull semantics rather
    than loosening the signature for everyone.

    JsonTest asserts EXACT output strings wherever a wire format is involved
    -- integers must not gain a decimal point, key order must be insertion
    order, payloads must round-trip byte-for-byte. A round-trip-only test
    would pass while both sides drifted together.

[x] PHASE 7 — TaskScheduler capability
    Source: AppSyncWorker, SocialBotWorker, NoraAutoTrainWorker (WorkManager)
    Android: WorkManager. Desktop: ScheduledExecutorService + registration with
    Windows Task Scheduler / systemd user timer so jobs survive restart.
    Must support: periodic, requires-idle, requires-charging, backoff.
    Done when: Nora auto-train fires on desktop after its interval.

    PARTIAL 2026-08-04 — interface and both implementations exist; the
    survive-restart half does NOT.

    core/Scheduling.kt defines TaskScheduler with periodic, one-shot, cancel
    and a requires-idle hint. JvmTaskScheduler runs on a daemon
    ScheduledExecutorService; AndroidTaskScheduler runs on a coroutine.

    WHY IT DOES NOT DELEGATE TO WorkManager, which the plan assumed it would:
    WorkManager persists a job by storing a ListenableWorker CLASS NAME and
    reconstructing it by reflection. A lambda cannot be persisted. So a
    TaskScheduler.Job carrying suspend () -> Unit is structurally unable to
    reach WorkManager. The three real background jobs therefore KEEP their
    existing WorkManager registrations, and this capability serves in-process
    work only. An interface that looked like it offered WorkManager's
    durability and silently did not would be the more dangerous design.

    STILL OPEN: Windows Task Scheduler / systemd user timer registration, and
    therefore "Nora auto-train fires on desktop after its interval" across a
    restart. Two gotchas already handled in JvmTaskScheduler and worth keeping
    if it is rewritten: scheduleWithFixedDelay not scheduleAtFixedRate (fixed
    rate queues missed runs during sleep and fires them back-to-back on wake),
    and every exception caught (a ScheduledExecutorService silently cancels a
    repeating task forever the first time it throws).

[x] PHASE 17 — App sync + launch statistics
    Source: AppSyncWorker, AppPackageReceiver, InstalledAppDao, AppLaunchStatDao

    DONE 2026-08-04. core/.../AppSync.kt, scheduled from desktop main() on the
    Phase 7 scheduler. Five-minute poll, first run two seconds after startup so
    a fresh install populates immediately instead of looking broken. Polling is
    a worse mechanism than a broadcast and is the only one available.

    This is what finally makes the taskbar prediction real -- it had the model
    but nothing to predict from.

    TWO THINGS THE TESTS CAUGHT, both invisible in normal use:

    1. recordLaunch seeds the row with a count of ZERO and then increments,
       which looks wrong and is not. Seeding 1 and incrementing records a first
       launch as two. Seeding 1 without incrementing is correct alone but loses
       a launch under a race -- two simultaneous launches both see increment
       return 0, both insert, the second is dropped by IGNORE. Seed 0 and
       always increment is correct in both cases. The first version of this
       function had the off-by-one and produced a plausible-looking but wrong
       hotseat, which nothing would ever have reported.

    2. An empty catalog scan does NOT clear the table. A scan returning nothing
       is far likelier to be a failed scan than a machine with no applications,
       and wiping on it empties the user's drawer for no reason.

    Full replace rather than a diff, because the table stores identity only and
    launch statistics live in a separate table -- tested to confirm they
    survive a resync.

    STILL OPEN: a WatchService on the Start Menu / applications directories
    would beat the poll.

[x] PHASE 19 — Icon packs
    Source: IconPackEngine (114)
    Android icon packs are APKs. Desktop analogue is XDG ICON THEMES, which
    XdgAppCatalog already resolves. On Windows, extract icons from .exe/.lnk
    (needs JNA ExtractIconEx or a small native helper) — this is the one place
    icons genuinely need native code.
    Done when: a theme change repaints the drawer and grid.

    PARTIAL 2026-08-04 -- and the framing in this phase is worth correcting.

    Android icon packs CANNOT be ported: they are APKs read through
    PackageManager, and there is neither an APK nor a PackageManager here. The
    genuine desktop equivalent is the XDG icon theme spec, which
    XdgAppCatalog already resolves when it finds an application's icon. So on
    Linux the feature effectively exists via a different mechanism, and there
    is deliberately NO icon-pack setting on the desktop settings page
    pretending otherwise.

    WINDOWS ICONS DONE 2026-08-04, and this phase's premise was wrong.

    The plan said extracting icons from .exe/.lnk "needs JNA ExtractIconEx or a
    small native helper -- this is the one place icons genuinely need native
    code". It does not. javax.swing.filechooser.FileSystemView.getSystemIcon(
    File, width, height) has been public API since Java 9, is implemented on
    the Windows shell exactly as ExtractIconEx would be, and costs no
    dependency at all. See desktop/.../SystemIcons.kt.

    Use the three-argument overload, not the one-argument one: the latter
    returns a 16x16 icon that looks terrible scaled to a desktop cell.

    Linux does not need any of this -- XDG desktop entries name an icon the
    theme spec resolves to a real file, which XdgAppCatalog already does. The
    helper returns null off Windows rather than pretending.

    LIVE RE-THEMING DONE 2026-08-04. ThemeRevision in PrismTheme.kt is a
    counter that appearance-setting writers bump; PrismTheme and the icon
    caches key on it, so a change repaints instead of waiting for a restart.
    A counter rather than observing the settings, because PrismSettings is a
    plain key-value store with no change notification -- deliberately, so it
    behaves identically on SharedPreferences and a properties file.

    PHASE 19 IS NOW COMPLETE for what it can be: XDG icon themes on Linux via
    XdgAppCatalog, Windows shell icons via SystemIcons, and live repaint on
    both. Android icon packs themselves remain unportable (they are APKs).

    THIS IS THE ONE PLACE ANDROID KEEPS ITS OWN IMPLEMENTATION ON PURPOSE, and
    it is worth understanding why before "unifying" it. DownloadManager is a
    SYSTEM SERVICE: the transfer continues after Prism is killed, survives a
    reboot, and handles connectivity changes. None of that is reimplementable
    inside an app process, and model files run to several gigabytes on a device
    whose OS kills backgrounded apps aggressively.

    JvmDownloader does not pretend to any of it. What it does instead is
    RESUME: the .part file is kept and continued with a Range request, so a
    download interrupted by quitting Prism restarts where it stopped. A server
    that ignores the range header answers 200 rather than 206, which is
    detected -- appending a full response onto a partial file would produce a
    corrupt archive of exactly the right size.

    The finished file is moved into place only on success. A truncated .gguf
    does not fail to load; it loads and generates nonsense.

[x] PHASE 39 — Encrypted SMS relay over the mesh
    NEW FEATURE, not in the Android build. Requires Phase 44.
    Phone relays SMS threads to desktop peers over the Prism mesh, encrypted,
    so texts appear on the PC without a Windows SMS API existing.
    Done when: a text received on the phone appears on the desktop.

    BUILT 2026-09-23, VERIFIED IN PART -- read the limit below before relying on
    it. core/.../messaging/SmsRelay.kt is the protocol, the envelope and the
    inbox; app/.../messaging/SmsRelayReceiver.kt is the sending half; the desktop
    listens on a daemon thread from Main.

    THE RECOVERY PHRASE IS THE SHARED SECRET. A relayed text crosses the mesh, so
    peers that are not the owner see the packet. The payload is sealed with a key
    derived from the wallet seed (CloudVault.Purpose.MESSAGING), which makes it
    readable on the owner's other devices and nowhere else. The precondition is
    stated rather than discovered: BOTH DEVICES MUST HOLD THE SAME PHRASE, and a
    desktop with its own fresh wallet receives packets it cannot open -- which is
    correct, and is what Status.WRONG_WALLET reports.

    The alternatives were a pairing code (another secret nobody writes down) or
    trusting the mesh (every peer reading your texts). Neither is better.

    WHAT IS VERIFIED: the envelope and the wire framing, by 17 tests in
    core/src/test/.../messaging/SmsRelayTest.kt -- seal/open round trip including
    non-ASCII, the plaintext NOT appearing in the ciphertext, a fresh nonce per
    seal, a different phrase failing to decrypt, the SAME phrase succeeding after
    a wipe and re-import, the refusal to seal with no wallet, framing rejecting
    other opcodes and runt packets, and inbox deduplication.

    WHAT IS NOT VERIFIED: an actual phone-to-desktop delivery. It has never run
    end to end, for two reasons worth recording. The desktop cannot decrypt at
    all yet -- WalletVault needs a cipher and desktop has none until PHASE 81 --
    and no Android device has been reachable to send from. So the transport is
    written and untested on the wire.

    THE TRANSPORT IS A STOPGAP AND SAYS SO. The mesh service is Android-only
    until PHASE 48, so the desktop listens to bare datagrams that use the SAME
    framing the mesh does: the PRISM header, a one-byte opcode, UDP 8081. Android
    sends through the real service unchanged. When 48 lands the desktop side
    becomes one more opcode and the listener is deleted.

    The receiver is OFF BY DEFAULT on the sending side. Forwarding somebody's
    texts off their phone is not something to enable on their behalf, even
    encrypted and even to their own machines.

[x] PHASE 43 — Brain visualizer
    Source: NoraBrainView (583) — TextureView + Canvas, live region activity

    It reads NoraTelemetry rather than the brain, and that indirection is what
    makes drawing at frame rate safe: the brain is mutating large tensors on a

    half-updated state or hold a lock the generator needs. It also costs nothing
    when idle -- NoraTelemetry.live is false outside a run.

    directions and that is what a predictive-coding hierarchy IS. One edge whose
    thickness is total traffic would hide the thing worth seeing: ascending error

    generation, so which mode the brain is in is visible at a glance.

    above, memory below. A force-directed layout would put the regions somewhere
    different every run and destroy the one property that makes the picture
    legible. Activity is auto-scaled across regions per frame, because the raw
    units differ by orders of magnitude between the retina and IT: on one absolute
    scale the retina is always saturated and IT never lights at all.

    Compose compares state by equality and a FloatArray mutated in place is equal
    to itself, so the canvas is invalidated by a revision counter rather than by
    the arrays. Without that it would never redraw.

    stated in the UI rather than hidden: the process outlives the window, so a
    user who closes Prism will see it still running, and Stop is how they end a run
    deliberately. An app that silently refused to quit would be worse than one
    that cancelled training.

    Stopping is COOPERATIVE. A trainer interrupted mid-example leaves the
    connectome half-updated and there is no way to tell that from a trained one
    afterwards, so it finishes the example, saves, and exits.

    consistent -- so a machine that is shut down loses at most one epoch rather
    than the whole run. Progress goes to the tray per EPOCH and not per example,
    because DesktopNotifier cannot replace a balloon (AWT has no handle to revoke
    one), so per-example notifications would be hundreds of popups. The frequent
    updates go to the page and the log instead.

    NOT scheduled retraining. The plan mentions Phase 7's scheduler as part of
    this; what is built is manual background training. Automatic retraining on a
    schedule is a separate decision about when it is acceptable to spend somebody's
    CPU, and it is not made here.

    A NOTE ON DOMAIN NAMES, recorded 2026-09-24 on instruction, because it applies
    to every phase in this section.

    THE SUPPORTED SUFFIXES ARE NOT LIMITED TO .p2p. A mesh name can be anything --
    .p2p, .com, .gov, .org, or a suffix nobody has ever registered. What makes a
    name a mesh name is that a peer announced a RECORD for it, which is a fact
    MeshDns holds; it is not something readable off the end of a string, and the
    code no longer pretends it is. `.p2p` remains a convention that cannot collide
    with the public internet, so it is still accepted before any record arrives.

    The consequence, stated rather than discovered: a hosted name SHADOWS the
    public one for devices on this mesh. That is the instruction working as asked.
    MeshWebHost.shadowsPublicName exists so a UI can say so, because somebody
    seeing a different site on one machine deserves to be told why.

    Places this was wrong and is now right: MeshDns resolves any registered name;
    MeshTls mints a leaf for any name; MeshWebHost hosts any name; and the desktop
    browser's isP2pDomain asks the registry instead of reading the suffix.

    out.

    NOT DNS IN THE PROTOCOL SENSE, and calling it DNS describes its job rather than
    its design. No zones, no TTL hierarchy, no authority, no recursion. The whole
    namespace is "sites people on this mesh are hosting" -- tens of entries -- and
    every peer holds all of it. A real resolver's machinery exists to avoid holding
    the whole internet, which is not this problem.

    LOOPBACK IS NEVER GOSSIPED. A host registers its own site against 127.0.0.1
    because that is where it serves from; broadcasting that would tell every peer
    the site is at THEIR loopback, and they would gossip it onward. The local
    address is substituted on the way out -- the one transformation this performs.

    SOURCE IS ASSIGNED BY THE RECEIVER. Everything learned from a peer is MESH
    whatever the sender called it: a peer claiming LOCAL would be claiming to be the
    authority for a name on this device, and source is what a later TLS decision
    (PHASE 51) rests on.

[x] PHASE 51 — TLS for mesh domains (any TLD)
    Source: PrismCertificateManager (162), PrismSslManager (69)
    BouncyCastle — already pure JVM, should port nearly unchanged.
    Root CA export.
    Done when: an https mesh site loads without a certificate warning.

    DONE 2026-09-24. core/.../core/MeshTls.kt, wired into MeshConnect so a peer speaking TLS is
    upgraded instead of refused. Verified with `prism tls`: the authority generates on first run and
    mints a leaf — tested against example.com, because the suffix is not what decides.

    ANY TLD, NOT JUST .p2p, as instructed. A leaf is minted for whatever name is asked for. The
    check that a name IS a mesh name belongs to MeshDns, which answers by holding a record, not by
    reading the end of a string.

    THE DEVICE IS ITS OWN AUTHORITY, because no public CA will ever issue for a name that has no
    registration and no public address. That means nothing trusts it until the user installs the
    root, and THAT IS NOT A FLAW TO BE HIDDEN: a private CA trusted automatically is precisely the
    attack a certificate store exists to prevent. `prism tls export` writes the PEM and prints the
    per-platform instructions; until then mesh https warns, correctly.

    EC RATHER THAN RSA. A P-256 key is generated in milliseconds where a 2048-bit RSA key is a
    visible pause, and a leaf is minted per domain on first contact. Every browser accepts it.

    THE SOCKET IS REWOUND, which is the part that would have been a silent bug. MeshConnect peeks one
    byte to tell a ClientHello from plain HTTP and pushes it back into a PushbackInputStream that the
    socket itself knows nothing about; an SSLSocket layered over the raw socket would start reading at
    the handshake's SECOND byte. MeshTls.Rewound is a delegating socket that hands over the stream
    holding that byte.

    files: a folder somebody pointed at by mistake — a home directory, a drive root — would otherwise

    Verified on the desktop end to end, by driving the window: the picker listed
    three live meshnet peers, choosing one opened the per-kind dialog with all four
    kinds, Offer recorded the pairing as pending and sent it, and Stop revoked it.
    The receiving half is a modal the window mounts for every page.

    MUTUAL CONSENT, AND IT IS NOT SYMMETRICAL POLITENESS. Two sets per device --
    what we will send, what we will accept -- and the RECEIVER authorises on
    receive. A sender deciding what another machine stores would make that
    machine's owner a bystander to a decision about their own device, and if the
    device is shared or somebody else's, the sender has no standing at all. A reply
    can never grant a kind that was not offered.

    IDENTITY IS A FINGERPRINT, NOT AN ADDRESS, and not the wallet address either.
    Derived from the vault namespace plus the machine name: an address is a DHCP
    lease, and a wallet address is a payment identity anybody can look up on chain
    -- using it here would link a user's devices to their balance for every peer
    that sees an offer go past.

    WHAT TRAVELS ON WHICH TRANSPORT. Messages, history and clipboard are small, so
    they ride the mesh datagram (opcodes 0x29/0x2A/0x2B, added to Android's
    existing service without touching the rest of it). AN APK DOES NOT: it is tens
    to hundreds of megabytes against a 16 KB ceiling, so the datagram carries the
    announcement -- package, label, version, size -- and the bytes come over the
    TCP PRISM_CONNECT channel, authorised per request against the peer's address.
    That is the same split the model shop already uses, reusing a tunnel known to
    work instead of inventing chunking over datagrams. Split APKs are why there are
    two routes rather than one: a base APK alone installs and then crashes looking
    for resources.

    NOTHING INSTALLS BY ITSELF. A received app lands in a staging directory and is
    listed as waiting; putting it through virtualization is the user's action, on
    the Virtualization page, where Play Protect and the sandbox rules apply. An APK
    that arrived over the network and installed itself is the exact shape of the
    thing those rules exist to prevent. "Automatically receiving" means the bytes
    arrive without being asked for again -- not that code runs without a decision.

    OFFERS ARE NOT PERSISTED. An offer is a live request from a device that is on
    the network now; one restored from disk days later would ask the user to
    consent to a situation that no longer exists and give them no way to check. An
    unanswered offer is simply re-sent next time both devices are up. Declining
    records an empty acceptance rather than leaving it pending, so it is asked once
    -- re-prompting on every launch is how people are trained to click through.

    WHAT IS NOT DONE. A desktop with no wallet can pair but cannot decrypt, and
    says so. The desktop cannot produce an app offer, only receive one -- there is
    no Android package on a PC.

    AMENDED 2026-09-24 ON INSTRUCTION. Four changes, all of which alter the model rather than adding
    to it.

    PAIRING IS MUTUAL NOW. Offering to share a kind is also agreeing to receive it, and accepting one
    is also agreeing to send it -- all trusted devices share and receive to and from each other. The
    two sets are still stored separately for two reasons that both still hold: a reply can only ever
    NARROW what was offered, in either direction, so a peer can never grant itself a kind nobody put
    on the table; and revocation is one-sided in practice, so the two sets are what lets that state be
    represented instead of guessed. Two tests cover it (`accepting is also agreeing to send` and
    `offering is also agreeing to receive`), and the consent wording on both platforms says "both
    ways" rather than naming one direction.

    A NEW PAIRING SENDS WHAT ALREADY EXISTS. Text conversations, browser history and the clipboard go
    across as soon as trust is confirmed, rather than the other device showing nothing until the next
    text arrives -- which reads as the pairing not having worked. TrustedSharing.backfill does the
    portable kinds; TrustedSharing.extraBackfill is the hook for what :core cannot produce, which on
    Android is the app catalogue and the phone's own SMS history read through the provider. Capped at
    500 messages and 300 history entries: everything would be tens of thousands of rows through a
    datagram transport, and what is older is still on the device that has it.

    TEXT MESSAGES ARE A CONVERSATION, IN BOTH DIRECTIONS.
      core/.../trusted/TrustedMessages.kt   the protocol, both ways
      core/.../messaging/SmsRelay.kt        Relayed gained `outgoing`
      app/.../trusted/TrustedRadio.kt       SmsManager, and the SMS provider for the backfill
      desktop/.../ui/MessagesPage.kt        threads and a reply box
      app/.../messaging/MessagingPageView   relayed threads beside the phone's own
      app/.../messaging/ConversationActivity   reads and sends them

    The receiving device shows the conversations in its Messages page, and a reply typed there is sent
    to the PHONE that owns the conversation, which puts it on its radio. THE ASYMMETRY IS THE FEATURE:
    a PC has no SIM, and pretending otherwise would mean either a paid gateway or a lie. A reply goes
    to ONE device -- the one that relayed that thread -- because broadcasting would have every paired
    phone send the same text, costing the user money and reaching the recipient three times.

    MMS AND RCS ARE NAMED AS GAPS rather than papered over. MMS needs a carrier MMSC transaction that
    Android exposes only to a system-privileged path; RCS runs through Google's Jibe stack with no
    public API at all. Text is what a non-default SMS app can send, so text is what this claims.

    APPS ARE ANNOUNCED AS A CATALOGUE, NOT AS FILES. A pairing sends the name of every launchable app
    on the phone; the icon is fetched over the TCP channel on demand and cached; the APK is fetched
    only when somebody picks one. That split is not an optimisation -- announcing the catalogue costs
    a few kilobytes and announcing the apps themselves would be tens of gigabytes, so without it the
    feature would be "wait an hour, then choose". Received apps appear IN THE APPS PAGE on both
    platforms (the drawer on Android, the apps list on desktop), carrying a synthetic component name
    so a tap is routed to the download instead of to Android.

    Clicking one downloads it if it is not here, then virtualizes it. On DESKTOP the download is where
    it stops, as instructed, and TrustedApps says so rather than appearing to launch something. On
    ANDROID an app that is already installed goes into the vault and runs virtualized; one that is not
    goes to the system installer, where the user confirms it and Play Protect scans it. AN APK THAT
    ARRIVED OVER THE NETWORK AND INSTALLED ITSELF IS THE EXACT THING THOSE RULES EXIST TO PREVENT, and
    Prism having a mesh is not a reason to be exempt from them.

[x] PHASE 61 — WireGuard

    THE CONFIGURATION HALF, done first and still the foundation: `prism vpn wg` generates a real X25519 keypair through :core's

        This device's public key: dUW+zuOxnGSYAoogTtjmUXkKb1hvc5Lxw9iUVEqCkn8=
        [Interface] PrivateKey / Address / DNS 127.0.0.1
        [Peer] PublicKey / Endpoint / AllowedIPs / PersistentKeepalive

    THE PRIVATE KEY GOES IN THE FILE AND NOWHERE ELSE. What the server is given is the PUBLIC key, in
    the peer block. That split is the whole security model and is worth not getting casual about: a
    generator that posted the private key to the server would be handing over the identity it had
    just created.

    COMPLETED 2026-09-24, in desktop/.../net/WireGuardInterface.kt. The criterion says a client
    CONNECTS to the desktop server, so what was built is the server half, not another client.

    A WIREGUARD SERVER IS NOT A DIFFERENT PROGRAM. An interface with a ListenPort and a peer block IS
    one; the config decides which end a device is. So: `prism vpn serve invite <name> <endpoint>`
    generates a peer, keeps its PUBLIC key, and prints the config for that device -- which is the only
    place its private key is ever written. `prism vpn serve up` writes this machine's config and starts
    the interface. A phone given that file connects to this machine.

    NO PEER GETS AllowedIPs WIDER THAN ITS OWN ADDRESS. On a server that field is not a permission to
    route, it is the cryptographic routing table -- the statement of which key may send from which
    address. A peer entry of 0.0.0.0/0 on a server lets any one peer impersonate every other, and it is
    the classic WireGuard misconfiguration. Each peer gets a /32.

    WINDOWS HAS NO wg-quick, AND AN EARLIER VERSION OF THIS CODE DID NOT KNOW THAT. wg-quick is a shell
    script the Windows distribution does not ship; what it ships is wireguard.exe, whose
    /installtunnelservice registers a config as a Windows service. Looking only for wg-quick reported
    "no WireGuard tool" on a machine with WireGuard installed and working -- the most misleading kind of
    wrong -- so VpnStack.wireGuardExecutable now looks for the right program per platform, including the
    install directory, since the Windows installer does not add itself to PATH.

    PRISM STILL DOES NOT SPEAK THE PROTOCOL, deliberately, and this is worth stating because the
    ingredients to try are all present: :core has X25519, and TunDevice has an adapter. WireGuard is
    Noise_IK with a handshake state machine, cookie replies under load, a nonce window and rekey timers
    on both ends. A hand-rolled version that ALMOST works is the worst possible outcome for a VPN,
    because it looks connected and fails cryptographically. wg-quick and wireguard.exe are the reference
    implementations, already privileged and already correct -- which is the same division of labour the
    Android side has, where com.wireguard.android:tunnel does the protocol and Prism does the config.

    VERIFIED AS FAR AS THIS MACHINE ALLOWS. `prism vpn serve invite phone 192.168.4.33` produced a real
    peer at 10.8.0.2 with a fresh key pair and a complete config; `prism vpn serve` prints the server

    C:\Program Files\WireGuard\wireguard.exe and reported, correctly:

        result   not up
        wireguard.exe was refused: bringing an interface up needs root or administrator rights.

    which is the honest failure and not a silent one. Creating the interface needs elevation this

    DNS 127.0.0.1 IS DELIBERATE in the generated config: it points a connecting client at PHASE 60's

[x] PHASE 63 — App whitelist / split tunneling
    Source: WhitelistActivity (123), WhitelistAdapter, AppUsageMonitor (68)
    UsageStats has no desktop equivalent — use process enumeration or drop
    the usage-based part and keep the manual whitelist.
    Done when: whitelisted apps bypass the tunnel.

    THE POLICY, done first: `prism vpn whitelist` lists, adds and
    removes, and also enumerates what is running so a choice can be made from a
    list rather than typed from memory.

    STORED AS EXECUTABLE NAMES, which is what a desktop has in place of a package name. It reuses the
    SAME setting the Android side writes rather than adding a second list, because it is the same
    policy and two would drift.

    ENFORCED 2026-09-24, in desktop/.../net/ProcessPorts.kt and core/.../TunnelRouter.kt. The note that
    used to sit here said enforcement was one line inside a tunnel that did not exist. The tunnel exists
    and it was not one line -- because a desktop has nothing like the mechanism Android uses.

    ANDROID HANDS A LIST OF PACKAGE NAMES TO VpnService.Builder AND THE KERNEL DOES THE REST: those
    applications never enter the tunnel, and Prism never sees their packets. A TUN adapter has no such
    facility. What arrives is an IP packet, and an IP packet does not say which program sent it. The
    only link back is the connection table the operating system already keeps -- local port to process
    id -- which is what ProcessPorts reads: `netstat -ano` on Windows, /proc/net plus a walk of
    /proc/<pid>/fd on Linux, and ProcessHandle for the name, so no subprocess is needed for that half.

    CACHED, WITH TWO DIFFERENT CLOCKS, and both are deliberate. A two-second life, because asking the
    operating system per packet would mean a subprocess per DNS query on the machine. And a 250ms floor
    for a MISS specifically -- without it, a program that opened its socket after the last read is
    absent from the table, is therefore not whitelisted, and stays tunnelled for the full two seconds no
    matter how many packets it sends. The floor closes that hole at a cost of at most four reads a
    second across the whole machine.

    "NOT KNOWN" AND "NOT WHITELISTED" GIVE THE SAME ANSWER, which is the single most important line of
    the design: both mean the packet goes THROUGH the tunnel. A bypass granted by accident is a privacy
    hole; a tunnel applied by accident is an inconvenience the user can see and fix. So every failure --
    an unparseable line, a process that has exited, a table that could not be read, a lookup that threw
    -- ends with the packet tunnelled. There is a test for the throwing case specifically, because the
    tempting way to write it grants a bypass to everything the moment the lookup breaks.

    THE WHITELIST IS CHECKED BEFORE THE BLOCKLIST, also a security property rather than an ordering
    accident. A whitelisted program is one the user has said Prism should keep its hands off; filtering
    its DNS anyway would make the whitelist a lie in exactly the case somebody added an entry to fix. So
    a bypassed query goes upstream verbatim -- no mesh lookup, no blocklist -- which is the answer the
    machine would have got with Prism not running.

    VERIFIED LIVE against the real connection table: `prism vpn selftest` opened a socket, found that
    java.exe owned port 63112, whitelisted it, and watched that packet bypass while an identical packet
    from an unlisted port was tunnelled.

    THE USAGE-BASED PART IS STILL DROPPED, as the plan allowed, and for the reason given before:
    UsageStatsManager ranks apps by screen time, and the desktop equivalent is a monitor watching what
    somebody uses all day -- a surveillance feature wearing a convenience hat. The list of running
    processes is offered instead, from ProcessHandle, which shows only this user's own.

    THE USAGE-BASED PART IS DROPPED, as the plan allowed. UsageStatsManager ranks apps by screen time
    to suggest what to whitelist; the desktop equivalent would be a per-process monitor watching what
    somebody uses all day, which is a surveillance feature wearing a convenience hat. Manual, from a

[~] PHASE 75 — Shell replacement (optional, opt-in)
    Windows per-user shell replacement via HKCU\...\Winlogon\Shell is

    BUILT 2026-09-24, in desktop/.../ShellReplacement.kt, with `prism shell` and a section in Prism
    Settings. [~] AND NOT [x] BECAUSE THE ROUND TRIP HAS NOT BEEN RUN HERE -- see the last paragraph.

    ONE REGISTRY VALUE: `Shell` under HKCU\Software\Microsoft\Windows NT\CurrentVersion\Winlogon.
    Absent on a normal installation, in which case Windows falls back to the machine-wide explorer.exe.
    Present, and the program it names starts at logon INSTEAD of Explorer -- which means no taskbar, no
    Start menu, no desktop icons and no Alt-Tab list, because every one of those is Explorer rather than
    Windows. Per-user, so it needs no administrator rights and cannot touch another account.

    UNDOING IT DELETES THE VALUE RATHER THAN WRITING explorer.exe BACK. Absence is the real default and
    is the state a machine that has never heard of Prism is in; writing explorer.exe would leave a
    per-user override that happens to agree with the machine-wide setting today and would quietly win
    against any future policy, kiosk configuration or corporate image that changed it.

    THE ESCAPE HATCH IS WRITTEN AND CHECKED BEFORE THE REGISTRY IS TOUCHED, and enable() REFUSES if it
    could not be written -- a shell replacement with no way back is a trap rather than a feature. It
    goes to two places because they fail differently: the Desktop, where somebody can see and
    double-click it, and the data directory, which always works but only helps somebody who knows it is
    there. So both paths are printed. Ctrl+Shift+Esc is named on the page as well, because Task Manager
    is handled by Windows rather than by the shell and opens with no shell running at all.

    A DEVELOPMENT BUILD IS REFUSED. The value is read by Windows at logon, long before a Gradle daemon
    or a JVM argument exists, so pointing it at a development launcher produces a session with no shell
    whatsoever. state() looks for a real installed .exe beside the runtime and says so when there is
    none -- which is exactly what it said when run here.

    SOMETHING ELSE'S SHELL IS NEVER OVERWRITTEN, in either direction. enable() refuses if a value is
    already set that Prism did not set, and disable() refuses to remove one -- whatever put it there
    expects it to be there.

    WHAT HAS NOT BEEN RUN, AND WHY IT IS [~]: roundTrip(), which is the function written specifically to
    satisfy this phase's criterion -- it sets the value, reads it back, removes it, reads it back again
    and leaves the machine exactly as it was found. The agent session that wrote this was denied
    permission to write that registry key, on the grounds that Winlogon\Shell is a persistence
    mechanism. That is a correct call by the sandbox and was not worked around. `prism shell test` runs
    it, prints PASS or FAIL, and changes nothing either way. Until somebody runs it, the read path is
    verified -- `prism shell` correctly reported the value absent and the build uninstalled -- and the
    write path is not.

    THE RULES WERE NEVER ANDROID-SPECIFIC, which is why this became a move rather than a port. Both of the
    behaviours the phase asked to preserve are pure logic:

      A STORED BASELINE, not an in-memory one, so a payment that landed while Prism was closed is still
      announced -- the comparison is against the last figure ever written down.

      A FIRST SIGHTING IS NOT A RECEIPT. Adding a coin that already holds funds, or restoring a wallet,

      has just recovered a wallet and is anxious about whether it worked. A null baseline records and says

    balance() because several things read a balance for reasons that are not the user looking at their
    wallet -- a send screen checking whether a spend fits, the compute market deciding whether a peer can
    pay. Announcing from those would deliver a receipt whenever an unrelated subsystem happened to poll.
    Both platforms' wallet pages call the observing one; nothing else does.

    ALSO ADDED: PrismSettings.clearLastSeenBalance, and WalletReceipts.forgetBaselines for a wallet being
    wiped. Without it the next wallet's first balance would be compared against the previous wallet's
    figures, and a restored wallet holding less than the old one would silently never announce again. The
    baseline is REMOVED rather than set to zero, because zero is a real balance and would re-announce

[x] PHASE 89 — On-device compilation (probably NOT wanted on desktop)
    Source: core/.../wallet/NativeBuildPlan.kt,
            app/.../wallet/NativeBuildEngine.kt, NativeCompilerActivity.kt.
    READ THIS BEFORE PORTING ANYTHING. The Android compiler exists solely to
    work around Android's refusal to execute binaries from app storage: the
    toolchain has to be a dlopen'd library, and every compiler invocation is
    spelled out because make and cmake cannot run at all. Desktop has none of
    those constraints — it can invoke a real toolchain, or simply ship
    prebuilt libraries.
    So the correct desktop answer is almost certainly to SKIP the compiler and
    ship RandomX and anything else as normal build artefacts. Port it only if
    there is a reason beyond symmetry with Android.
    What IS worth taking: the library-loading path, so a desktop build can use
    a RandomX built elsewhere.


    DONE 2026-09-24, AND THE ANSWER IS THE ONE THE PHASE PREDICTED: the on-device compiler is NOT ported,
    and the library-loading path is what was taken.

    WHY NOT: that compiler exists solely because Android refuses to execute a binary from app storage -- the
    toolchain has to be a dlopen'd library, every invocation is spelled out by hand, and make and cmake
    cannot run at all. A desktop has cmake, a real compiler and permission to run them. Porting the
    workaround would have been porting the workaround.

    WHAT WAS BUILT INSTEAD: desktop/src/main/cpp/randomx/CMakeLists.txt and a `:desktop:buildRandomx` task,
    compiling THE SAME VENDORED SOURCE the APK uses -- ../../app/src/main/cpp/randomx, not a second copy.
    Two copies of a hashing implementation is two revisions of a consensus-critical algorithm, and a mesh
    where one device's RandomX disagrees with another's produces shares that are silently rejected.

    RandomXNative MOVED TO :core, so the Kotlin side is identical on both platforms, and NativePayload loads
    randomx_jni like every other library. It is last in the load order and absent on a machine that has not
    run the build task, which costs mining and nothing else.

    THREE REAL PROBLEMS, FOUND BY ACTUALLY BUILDING AND RUNNING IT:

      1. randomx_jni.cpp included <android/log.h> UNCONDITIONALLY, so the translation unit could not be
         compiled for a host at all. gguf_bridge.cpp had the identical problem and the identical fix.

      2. MSVC CANNOT READ gas SYNTAX. The JIT's static stubs are hand-written assembly and upstream ships
         both jit_compiler_x86_static.S (gas) and .asm (MASM). Handing the .S to MSVC assembled to nothing
         and produced a link full of unresolved stubs -- randomx_program_prologue and friends -- rather than
         a readable error. The CMake picks the file by assembler. cpu.cpp and the two argon2 SIMD variants
         also had to be listed explicitly, which the NDK build got from upstream's own CMakeLists.

      3. THE JIT WAS SILENTLY OFF, AND THIS IS THE ONE THAT MATTERED. virtual_memory.c's Prism shim -- a
         dual mapping that works around Android's W^X -- is excluded on Windows, and its stub returned 0
         from randomx_prism_exec_supported(). The JNI bridge reads that as "this device will not execute
         memory the app allocated", dropped RANDOMX_FLAG_JIT and used the interpreter:

             rate    2.0 H/s on one thread

         The desktop build looked like it worked and mined at a rate that would never find a share. On
         Windows VirtualAlloc with PAGE_EXECUTE_READWRITE does exactly what RandomX's own allocator asks
         for, so the stub now reports 1 and RandomX uses its own allocator. RANDOMX_FLAG_SECURE is now
         Android-only for the same reason -- it costs throughput to solve a problem a desktop kernel does
         not have.

             rate    39.2 H/s on one thread

         AND THE HASH IS BYTE-IDENTICAL EITHER WAY (b0e8a1af9d5a9569...), which is the part that matters for
         a pool: the JIT and the interpreter agree, so shares computed on a desktop verify against work from
         a phone.
    Done when: either RandomX mining works on desktop from a shipped library,
    or a deliberate decision is recorded here that on-device compilation is
    not wanted on desktop.

[x] PHASE 92 — Plugin pages on desktop
    Source: app/.../DynamicPageLoader.kt, PluginPageDiscovery.kt.
    Already named as unported in LauncherShell. Android loads a View class out
    of another APK; desktop would scan a plugins directory for JARs and load a
    Composable or a Swing component through a defined SPI.
    This needs a DECISION before any code: the Android plugin contract is
    "return an Android View", which has no desktop equivalent. Either define a
    second, desktop-shaped contract, or define one neutral contract both
    platforms implement. Do not fake an Android View on desktop.
    Done when: a sample plugin JAR loads as a desktop page, and the contract
    is documented well enough for a third party to build against it.

    DONE 2026-09-24. core/.../plugins/PrismPlugin.kt is the contract; desktop gets ui/PluginsPage.kt and
    ui/PluginRenderer.kt; :sample-plugin is a working JAR built by every build.

    THE DECISION THE PHASE ASKED FOR: ONE NEUTRAL CONTRACT, AND A PLUGIN RETURNS UI AS DATA.

    Neither existing option worked. Android plugins return an `android.view.View`, and the plan forbids
    faking one here. A Compose `@Composable` is not neutral either -- it is a compiler-plugin-transformed
    function type, it cannot be named in a plain interface a third party compiles against without pulling
    Compose into their build, and the Android app is not Compose yet. So a plugin returns a PluginNode tree
    -- text, rows, columns, buttons, fields, images, progress -- and each host draws it with its own
    toolkit.

    WHAT THAT COSTS, AND IT IS REAL: a plugin cannot draw anything the node set does not describe. No
    canvas, no animation, no gesture beyond a click. That is the price of being renderable by two toolkits
    that share nothing, and the alternative -- a contract per platform -- means writing and testing the UI
    twice for what a plugin page usually is: a dashboard, a converter, a feed. Something that needs to draw
    belongs in Prism rather than beside it.

    THE ACTION IS AN ID, NOT A LAMBDA, which is what keeps the tree data. The host dispatches an action and
    then calls content() again, so a plugin changes its page by returning a different tree -- the same way it
    built the first one. A lambda would mean the host holding references into plugin code across refreshes.

    THE SAMPLE IS A GRADLE MODULE, NOT A DOCUMENTATION SNIPPET, because a sample that lived only in prose
    would rot the first time the contract changed. It depends on :core and nothing else -- no Compose, no
    Android, no Swing -- and if it ever needs more than that, the contract has leaked. `compileOnly`, so it
    does not bundle a second copy of :core with its own PrismSettings pointing at nothing.

    VERIFIED END TO END with `prism plugins allow`: discovery, the consent gate, classloading,
    instantiation, a content() call printed as an outline, a dispatched action reported as handled, and the
    tree confirmed to have changed afterwards.

    EVERY CALL INTO A PLUGIN IS GUARDED, and failures are drawn ON THE PAGE rather than only logged -- the
    person who installed the plugin is the one who needs to know it is broken, and they are looking at the
    page. content() is always called off the UI thread, because the contract permits it to read files and
    the network and a plugin author has no way to discover they froze Prism.

    STILL OFF BY DEFAULT. A plugin is loaded into Prism's process by a classloader whose parent is Prism's,
    so it can do anything Prism can. On Android a plugin at least had to be an installed package; a JAR in a
    folder carries no such consent.

    content is the same PluginNode tree the page uses, through the same renderer. A widget that looked like a
    different product from its own page would be the wrong outcome.

    widget is identified by its class name, because that is what the loader finds it by and there is nothing
    to orphan. Merging them into one item with a nullable id would have meant every site asking which kind it
    held, and the AppWidget cleanup path calling deleteAppWidgetId on something with no id.

    THE OCCUPANCY MACHINERY IS REUSED, NOT COPIED. Both widget kinds now go through one `occupy`, because the
    invariant -- every cell has exactly one owner, and a covered cell points back at its owner's index -- is
    what the grid, the drag-and-drop and the delete zone all depend on. Two implementations is two places for
    it to go subtly wrong.

    ADDING THE TYPE BROKE TWELVE `when` EXPRESSIONS AND THE COMPILER FOUND ALL OF THEM, which is the argument
    for a sealed class. Nine were on Android, where a plugin widget cannot be drawn yet -- its grid is Views
    and it has no host for this contract -- so each joins the branch that already handles "a widget-shaped
    cell this path does not draw". Nine lines changed in :app, and no `else` was added anywhere: a genuinely
    new item type later should break the build again rather than being silently swallowed.

    PLACEMENT IS OFFERED FROM THE PLUGINS PAGE, not the grid, because `widget` is a property on an INSTANCE

    "run number 4" is the proof the vault is doing its job: the app's own preferences survived being
    sealed and unsealed three times, and nothing but interpreted app code ever wrote them. The count
    is what caught the last bug of the phase, too -- it went 1, 2, 3, 1, 2, 1 across runs, because
    `getSharedPreferences(name, mode)` was reading ARGUMENT 0 for the name and argument 0 is the
    RECEIVER. The file was therefore named after the Context object, whose toString carries its
    identity hash -- which is stable across runs with an identical allocation order, so preferences
    persisted for several runs and then silently started from empty after an unrelated change. The
    same line meant two components sharing a preferences name did not share state, and the vault grew
    by a whole extra file every time the hash moved. Preferences are now keyed by name, cached per
    name so a write through one handle is visible through another, and the name is sanitised before
    it reaches the filesystem.

    A CLASSLOADER CANNOT DO THIS, which is the single biggest difference from the mobile technique.
    The phase said points one to three were "ordinary JVM work" -- they are not, because dex is not
    JVM bytecode and `ClassLoader.defineClass` cannot read it. The options were translating dex to
    class files (a bytecode writer, and every `invoke` still points at a framework that is not there)
    or interpreting it. Interpreting won because it gives ONE function through which every call that
    leaves the app's code must pass, and that function is the framework surface the phase said was
    the whole problem.

    WHAT THE DEX READER HANDLES, because each of these was a bug first: multidex sorted NUMERICALLY
    (classes2 before classes10); class_data indices as DELTAS; SLEB128 sign-extended; strings as
    MUTF-8 rather than UTF-8, including the C0 80 encoding of NUL and CESU-8 surrogate pairs. Prism's
    own APK reads as 33 dex files and 27,932 classes.

    METHOD BODIES ARE READ ON DEMAND. Decoding every method eagerly filled a 4 GB heap before an
    app's onCreate finished -- and it did not fail as an out-of-memory in the reader, it failed as
    `OutOfMemoryError` from `LinkedHashSet.add` inside an app's `<clinit>`, which looks exactly like
    an interpreter bug. A startup executes a few hundred methods out of half a million, so the offset
    is kept and the body is decoded and cached when the method first runs.

    TWO MORE BUGS CAME OUT OF GETTING THAT FAR, both about values the interpreter never wrote:

      * AN UNWRITTEN FIELD READ NULL WHERE DALVIK GUARANTEES ZERO. An `int` field got away with it --
        reading null as an integer gives 0 -- and a `long` or `double` field did not. The null reached
        `Math.min(JJ)J` at the framework surface, reflection refused null for a primitive parameter,
        and the call was recorded as an unimplemented method on `java.lang.Math`: the report blamed
        the JDK for an uninitialised field in the app. Instance fields are now prefilled from the
        whole hierarchy's declared types and an unassigned static reads its type's zero. Fixing it
        took the startup from 69,000 interpreted instructions to 202,000.
      * WIDE ARGUMENTS WERE IDENTIFIED BY LOOKING AT THE VALUE. A `long` occupies two register slots
        and is passed once, and the first version skipped the second slot when the first held a Long
        -- correct whenever the register holds what the signature says and wrong otherwise. A wide
        register holding null shifted every later argument by one. The method's own descriptor says
        which parameters are wide, and now decides it.

    THE INTERPRETER IS CHECKED AGAINST COMPILED KOTLIN, which is the part that makes any of this
    trustworthy. `prism virtualapp verify` runs 32 pure methods out of the APK's R8-compiled dex
    through the interpreter and compares each answer with Prism's own :core compiled from the same
    source. 32/32 agree. "It ran and did not crash" is not evidence an interpreter is correct: a
    mis-decoded arithmetic opcode produces a wrong NUMBER, and a mis-decoded packed-switch quietly
    takes the else branch.

    THE BUGS THAT SUITE AND THAT APP FOUND, each of which was silent:

      * `if-eqz`/`if-nez` TREATED EVERY NON-NULL APP OBJECT AS NULL. One opcode tests an int against
        zero and a reference against null, and the register was being read numerically -- whose
        fallback is 0. So every `if (x != null)` on an interpreted object took the null branch. It
        surfaced as `Intrinsics.checkNotNullParameter` throwing on a value the trace showed was
        plainly present, six `<clinit>` failures deep in kotlinx.coroutines.
      * `if-eq`/`if-ne` compared two references as `0 == 0`, so unrelated objects were equal.
      * FLOAT REGISTERS HOLD IEEE BITS, not numbers. `const v0, 0x3f400000` is how 0.75f arrives, and
        reading it numerically made Kotlin's `mapCapacity(8)` return 1,065,353,216 -- the bit pattern
        of 1.0f. Every `setOf` and `mapOf` in the app then asked for a billion-bucket hash table.
        Twenty-four integer cases had agreed perfectly while every float in the app was wrong by nine
        orders of magnitude; the suite now covers float and double.
      * `cmp-long` read vAA and vBB instead of vBB and vCC -- comparing the destination register
        against the first operand, and out of bounds whenever vAA was the last register. cmpl and
        cmpg were a single implementation, which makes one of `a < b` and `a > b` wrong for NaN.
      * `const-class` put the class's NAME in the register, so every `X::class.java` was a String and
        the first `getName()` on it arrived as an unimplemented call on java.lang.Class. A dex-only
        type is now a `DexClass`, which is also what `getClass()` on an app object returns.
      * MISSING OPCODES THAT ARE UNAVOIDABLE RATHER THAN EXOTIC: `filled-new-array` (every enum's
        generated `$values()`), `fill-array-data`, `packed-switch` and `sparse-switch`. A missing
        switch is worse than a crash -- the `when` silently takes its else branch.
      * AN APP'S OWN ARRAY OVERRUN was reported as an interpreter fault. It is now a DalvikThrow the
        app can catch, and the interpreter's own register-index diagnostic names the opcode and
        address.
      * A FRAMEWORK CONSTRUCTOR'S RESULT WENT NOWHERE. Dex makes an object then runs its constructor;
        the JVM cannot run a constructor on an existing object, so the surface constructs again -- and
        a constructor is not followed by `move-result`, so `new File(path)` left a placeholder in the
        register and every later `exists()` arrived as an unimplemented call on a faked java.io.File.
      * AN APP OBJECT WAS BEING REPLACED BY ITS OWN SUPERCLASS INSTANCE. `class Worker : Thread()`
        calls `Thread.<init>`, and adopting that result threw the app's object away -- fields,
        overrides, identity. The real instance is now kept BESIDE it, so `setName` and `start` have
        somewhere to go, and a Thread host is built around a Runnable that calls back into the
        interpreter (daemon always: a virtualized app must never be why Prism cannot exit).

    THE FRAMEWORK SURFACE grows app by app, which the phase anticipated. What is there now: Log,
    Context identity and directories, SharedPreferences (one object for the preferences and the
    editor, as Android's own are), Build.VERSION, Looper and Handler, SystemClock, Process, Trace,
    StrictMode, Environment, Application's own no-ops, and the atomic field updaters.

    reportedSdkInt IS 24 DELIBERATELY: high enough to miss the pre-Marshmallow permission paths, low
    enough to miss scoped storage, foreground services and notification channels. It is the level
    with the smallest surface requirement.

    THE FIELD UPDATERS ARE REAL, NOT FAKED. `AtomicReferenceFieldUpdater.newUpdater` needs a JVM
    field for Unsafe to address and an interpreted object has none, so the real call threw, was
    swallowed, and returned null -- and kotlinx.coroutines keeps its updaters in static finals, so a
    null updater meant a null from every later `get`. The surface's updater operates on the app
    object's field map and synchronizes on the object: heavier than a CAS, and a `compareAndSet` that
    lies is how a coroutine gets resumed twice.

    AN INTERPRETED OBJECT CAN BE HANDED TO REAL JVM CODE, through `java.lang.reflect.Proxy` over the
    interfaces its class declares -- so an app's Runnable goes to an executor and its ThreadFactory to
    `Executors`, for real. The boundary translates BOTH WAYS: proxies coming back become app objects
    again at the one point every call passes through, and an untyped result is conformed to the
    declared return type (an app's `hasNext()` returns 1, and a proxy declared `boolean` must hand
    back a Boolean). Proxy cannot extend a class, which is a real limit, recorded rather than hidden.

    OVERLOADS ARE CHOSEN BY THE DEX DESCRIPTOR. Choosing from the VALUE cannot work, because the
    register has no type: a float constant is an Int holding bits and `append(int)` accepts it
    happily, so `"ratio " + 133.33333f` printed 1124422997 from a method doing exactly as asked.

    KOTLIN'S `Intrinsics` IS ANSWERED BY THE SURFACE even though the app ships its own copy -- the
    only class treated that way, and the list is kept short on purpose.
    `createParameterIsNullExceptionMessage` builds its message by reading its own JVM stack trace to
    find the caller, and interpreted code has no frame there. Every genuine null-check failure
    therefore arrived as `ArrayIndexOutOfBoundsException: index 51 out of bounds for length 51` from
    inside Kotlin's message builder, hiding what was actually null. It now throws the
    NullPointerException the app expects, naming the parameter the dex already carries as a constant.

    A JVM METHOD THAT THROWS IS THE APP'S EXCEPTION, NOT A GAP. Swallowing it made the surface report
    "java.util.List.set -- unimplemented" for an app indexing past the end of its own list, so the
    report whose job is to say what to implement next pointed at the JDK -- and the app never got the
    exception its own catch was waiting for.

    SOME CALLS ARE REFUSED ON PURPOSE AND ARE NOT GAPS:
    `Thread.setDefaultUncaughtExceptionHandler` would put an interpreted handler on the JVM Prism
    itself runs on; `System.exit` and `Runtime.halt` would take Prism down with the app;
    `Runtime.exec` and `ProcessBuilder.start` would run a real process with Prism's privileges.
    Each answers with the success the app expects and does nothing.

    THE VAULT CAME FIRST, as the phase required, and is verified rather than asserted:
    PASSPHRASE_LENGTH = 60 alphanumerosymbolic characters, look-alikes omitted, drawn uniformly and
    then CHECKED for one of each class (assembling one class at a time biases the distribution).
    KDF_ROUNDS = 210,000, OWASP's 2023 figure for SHA-256. The passphrase is NOT cached in a field,
    because a held copy is one an app could reflect over. `seal()` writes to data.sealed.part and
    renames, and deletes the live plaintext in a `finally` -- so an interrupted seal cannot leave a
    truncated vault and a crashed run cannot leave plaintext. `prism virtualapp vault` sealed 337
    bytes, confirmed the plaintext absent from the sealed file, round-tripped identically and caught
    tampering on the GCM tag.

    ONE HONEST LIMITATION, STATED ON SCREEN RATHER THAN BURIED HERE: Prism's runtime and the
    virtualized app share one JVM, so a hostile app that reflected over Prism's own classes could
    reach the passphrase. Closing that needs the runtime in a second process. The vault text says so.

    PRISM'S OWN APK IS THE HARD CASE AND GETS FURTHER THAN EXPECTED. `prism virtualapp run
    com.prism.launcher` interprets 202,463 instructions of PrismApp.onCreate with ONE unanswered
    framework call, and the app's own log is the report:

        I/PrismLogger:    Prism Diagnostics Initialized. Logging to ...virtualapps-live/
                          com.prism.launcher/files/external/Prism/diagnostics.log
        I/PrismLock:      Lock gate installed
        I/PrismSearch:    No index on disk yet -- first crawl will build one.
        D/PrismSearch:    SUCCESS: Prism search listening on http://127.0.0.1:33840
        D/PrismSearchHost SUCCESS: Claimed prism.com -> 127.0.0.1 (local)
        D/PrismTunnel:    Tunneling disabled in settings; Backbone idling.

    Prism's search server is genuinely listening on that port -- a real socket, opened by interpreted
    dex, out of the encrypted vault. Its diagnostics log is a real file inside the vault.

    WHERE IT STOPS IS THE PHASE'S OWN PREDICTION, ARRIVING ON SCHEDULE:

        IllegalStateException: WorkManager is not initialized properly. You have explicitly disabled
        WorkManagerInitializer in your manifest, have not manually called WorkManager#initialize at
        this point, and your Application does not implement Configuration.Provider.
            at androidx.work.impl.WorkManagerImpl.getInstance +40
            at androidx.work.WorkManager.getInstance +0
            at com.prism.launcher.PrismApp.onCreateMainProcess +196
            at com.prism.launcher.PrismApp.onCreate +410

    THAT IS NOT AN INTERPRETER BUG. It is the app correctly detecting that a framework component it
    depends on is absent -- WorkManager initialises itself through a ContentProvider the manifest
    declares, and this surface has no ContentProviders. The phase said it plainly: "an app that only
    needs Activity, View and SharedPreferences should run long before one that needs a
    ContentProvider." PrismApp needs one, 410 instructions into its own onCreate and after thirty
    subsystems have already started.

    THE DIAGNOSTICS ARE PART OF THE DELIVERABLE, because without them none of the bugs above were
    findable. A DalvikThrow collects the interpreted frames as it propagates, each with its opcode,
    address and arguments; the surface report names the receiver's real type beside each unanswered
    call; and `prism virtualapp call` and `methods` run one method at a time against a known answer.
    A JVM stack trace here is `execute` and `invoke` alternating, as deep as the app's call stack, and
    says nothing about the app.

FIX 2026-10-01 — Downloaded models disappeared from Prism Desktop on restart
================================================================================

    Reported as "downloaded models on Prism Desktop stop showing up when Prism is
    restarted". core/.../messaging/ModelRegistry.kt.

    TWO HALVES, AND EITHER ALONE WOULD HAVE EXPLAINED IT BADLY.

    1. TWO DIVERGENT MODEL DIRECTORIES, UNDER A COMMENT CLAIMING THEY WERE SHARED.
       Downloads landed in dataDir()/models and the page listed
       documentsDir()/Models. A model downloaded in one session was therefore real,
       on disk, and invisible. `directory()` is now documentsDir()/Models,
       `legacyDirectory()` is the old path and is STILL SCANNED, and `reconcile()`
       adopts what it finds there -- so a user who already downloaded models gets
       them back without being told to move anything. All four models already on
       this machine were recovered automatically.

    2. THE DOWNLOAD LISTENER WAS REGISTERED IN A PAGE-SCOPED COROUTINE, so leaving
       the page lost the registration and the completed download was never
       installed. `watchDownloads()` now CHAINS the previous `onProgress` listener
       rather than replacing it, which was the other half: two watchers each
       thought they owned the slot.

    The page's own `watchAndImport` was renamed `watchForDisplay`, because it only
    ever refreshed the list -- the name claimed it was the thing doing the
    importing, which is why the missing installation step was looked for in the
    wrong file.
