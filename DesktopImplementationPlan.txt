--------------------------------------------------------------------------------
ARCHITECTURE RULES (apply to every phase)
--------------------------------------------------------------------------------

  * :core is a plain Kotlin/JVM module. android.jar is NOT on its classpath.
    An "import android.*" in :core is a compile error, by design. Never add the
    Android plugin to :core to make something compile.
  * Platform differences go behind CAPABILITY interfaces in com.prism.core,
    defined by what Prism NEEDS, not by what Android offers. Do not create
    IPackageManager / IContext / IBitmap. See AppCatalog and PlatformHost for
    the pattern that is already established.
  * Persistence keys and store names MUST NOT CHANGE when moving code to :core.
    Existing Android installs read those exact strings. Changing one silently
    resets a user. See NoraConfig.loadGeometry for the migration pattern.
  * Every platform adapter should be THIN. If an adapter grows logic, the
    interface asked for a mechanism instead of a capability — redesign it.
  * Android must keep working after every phase. This is one product, not a
    fork.

--------------------------------------------------------------------------------
WHAT HAS NO DESKTOP EQUIVALENT (do not pretend otherwise)
--------------------------------------------------------------------------------

  * SMS / MMS — Windows has no public API, Linux needs a cellular modem.
    Desktop Messages is AI-only. Phase 40 covers relaying SMS from the phone
    over the mesh instead, which is the real answer.
  * Android Virtualization Framework (android.system.virtualmachine) —
    desktop uses QEMU/libvirt. That is a REIMPLEMENTATION, not a port.
  * LocalOnlyHotspot / WifiP2p — Windows netsh, Linux nmcli/hostapd. Also a
    reimplementation.
  * ShakeDetector — no desktop analogue. Rebind to a hotkey.

[x] PHASE 6 — Replace org.json with kotlinx.serialization
    Source: AgenticWireFormats, AgenticEngine, PrismMeshService, P2pDnsManager,
            P2pModelRegistry, CloudAiService, NebulaSocialManager,
            ModelDiscoveryService, AccessPointModel (toJson x4)

    Done when: no org.json import remains outside :app UI code.

    DONE 2026-08-04. Zero org.json references remain anywhere, including the
    UI code the criterion allowed to keep them.

    NOT converted to @Serializable data classes, and that was the whole
    decision. 196 JSONObject/JSONArray references across 20 files, and those
    objects ARE the wire format -- mesh gossip, DNS records, the model
    registry, agentic tool-calling, cloud AI request bodies. Twenty separate
    hand-conversions means twenty separate chances to change a payload
    subtly, and the failure lands on a peer's machine or a third-party API,
    not here. So core/json/Json.kt reimplements org.json's API on
    kotlinx.serialization and the call sites changed only their import.
    NoraFeedback's parser untouched, as instructed.

    One real incompatibility, worth knowing if this pattern is reused:
    org.json's optString(key, fallback) types its fallback as a Java platform
    type, so optString("ip", null) compiles there. The portable one types it
    non-null so the other 31 call sites keep returning String. Fixed at the
    single call site (DiscoveryEngine) with explicit isNull semantics rather
    than loosening the signature for everyone.

    JsonTest asserts EXACT output strings wherever a wire format is involved
    -- integers must not gain a decimal point, key order must be insertion
    order, payloads must round-trip byte-for-byte. A round-trip-only test
    would pass while both sides drifted together.

[x] PHASE 7 — TaskScheduler capability
    Source: AppSyncWorker, SocialBotWorker, NoraAutoTrainWorker (WorkManager)
    Android: WorkManager. Desktop: ScheduledExecutorService + registration with
    Windows Task Scheduler / systemd user timer so jobs survive restart.
    Must support: periodic, requires-idle, requires-charging, backoff.
    Done when: Nora auto-train fires on desktop after its interval.

    PARTIAL 2026-08-04 — interface and both implementations exist; the
    survive-restart half does NOT.

    core/Scheduling.kt defines TaskScheduler with periodic, one-shot, cancel
    and a requires-idle hint. JvmTaskScheduler runs on a daemon
    ScheduledExecutorService; AndroidTaskScheduler runs on a coroutine.

    WHY IT DOES NOT DELEGATE TO WorkManager, which the plan assumed it would:
    WorkManager persists a job by storing a ListenableWorker CLASS NAME and
    reconstructing it by reflection. A lambda cannot be persisted. So a
    TaskScheduler.Job carrying suspend () -> Unit is structurally unable to
    reach WorkManager. The three real background jobs therefore KEEP their
    existing WorkManager registrations, and this capability serves in-process
    work only. An interface that looked like it offered WorkManager's
    durability and silently did not would be the more dangerous design.

    STILL OPEN: Windows Task Scheduler / systemd user timer registration, and
    therefore "Nora auto-train fires on desktop after its interval" across a
    restart. Two gotchas already handled in JvmTaskScheduler and worth keeping
    if it is rewritten: scheduleWithFixedDelay not scheduleAtFixedRate (fixed
    rate queues missed runs during sleep and fires them back-to-back on wake),
    and every exception caught (a ScheduledExecutorService silently cancels a
    repeating task forever the first time it throws).

[x] PHASE 17 — App sync + launch statistics
    Source: AppSyncWorker, AppPackageReceiver, InstalledAppDao, AppLaunchStatDao

    DONE 2026-08-04. core/.../AppSync.kt, scheduled from desktop main() on the
    Phase 7 scheduler. Five-minute poll, first run two seconds after startup so
    a fresh install populates immediately instead of looking broken. Polling is
    a worse mechanism than a broadcast and is the only one available.

    This is what finally makes the taskbar prediction real -- it had the model
    but nothing to predict from.

    TWO THINGS THE TESTS CAUGHT, both invisible in normal use:

    1. recordLaunch seeds the row with a count of ZERO and then increments,
       which looks wrong and is not. Seeding 1 and incrementing records a first
       launch as two. Seeding 1 without incrementing is correct alone but loses
       a launch under a race -- two simultaneous launches both see increment
       return 0, both insert, the second is dropped by IGNORE. Seed 0 and
       always increment is correct in both cases. The first version of this
       function had the off-by-one and produced a plausible-looking but wrong
       hotseat, which nothing would ever have reported.

    2. An empty catalog scan does NOT clear the table. A scan returning nothing
       is far likelier to be a failed scan than a machine with no applications,
       and wiping on it empties the user's drawer for no reason.

    Full replace rather than a diff, because the table stores identity only and
    launch statistics live in a separate table -- tested to confirm they
    survive a resync.

    would beat the poll.

[x] PHASE 19 — Icon packs
    Source: IconPackEngine (114)
    Android icon packs are APKs. Desktop analogue is XDG ICON THEMES, which
    XdgAppCatalog already resolves. On Windows, extract icons from .exe/.lnk
    (needs JNA ExtractIconEx or a small native helper) — this is the one place
    icons genuinely need native code.
    Done when: a theme change repaints the drawer and grid.

    PARTIAL 2026-08-04 -- and the framing in this phase is worth correcting.

    Android icon packs CANNOT be ported: they are APKs read through
    PackageManager, and there is neither an APK nor a PackageManager here. The
    genuine desktop equivalent is the XDG icon theme spec, which
    XdgAppCatalog already resolves when it finds an application's icon. So on
    Linux the feature effectively exists via a different mechanism, and there
    is deliberately NO icon-pack setting on the desktop settings page
    pretending otherwise.

    WINDOWS ICONS DONE 2026-08-04, and this phase's premise was wrong.

    The plan said extracting icons from .exe/.lnk "needs JNA ExtractIconEx or a
    small native helper -- this is the one place icons genuinely need native
    code". It does not. javax.swing.filechooser.FileSystemView.getSystemIcon(
    File, width, height) has been public API since Java 9, is implemented on
    the Windows shell exactly as ExtractIconEx would be, and costs no
    dependency at all. See desktop/.../SystemIcons.kt.

    Use the three-argument overload, not the one-argument one: the latter
    returns a 16x16 icon that looks terrible scaled to a desktop cell.

    Linux does not need any of this -- XDG desktop entries name an icon the
    theme spec resolves to a real file, which XdgAppCatalog already does. The
    helper returns null off Windows rather than pretending.

    LIVE RE-THEMING DONE 2026-08-04. ThemeRevision in PrismTheme.kt is a
    counter that appearance-setting writers bump; PrismTheme and the icon
    caches key on it, so a change repaints instead of waiting for a restart.
    A counter rather than observing the settings, because PrismSettings is a
    plain key-value store with no change notification -- deliberately, so it
    behaves identically on SharedPreferences and a properties file.

    PHASE 19 IS NOW COMPLETE for what it can be: XDG icon themes on Linux via
    XdgAppCatalog, Windows shell icons via SystemIcons, and live repaint on
    both. Android icon packs themselves remain unportable (they are APKs).

    NO DEPENDENCY WAS NEEDED. java.net.URL has an FTP handler built in: an
    ftp:// URL ending in a slash returns a directory listing and one ending in
    a filename returns the file. core/.../NetworkStorage.kt is the listing
    parser and URL construction around that.

    server emits regardless of host OS, plus the Windows/IIS format. The parser

    server banner or a "total 48" line accepted as a filename produces a folder
    the user can click that cannot exist. Pinned by NetworkStorageTest.

    Two details worth keeping: the ";type=d" hint on directory URLs (without it
    some servers serve a directory as a zero-byte file), and percent-encoded
    credentials (a password containing @ otherwise breaks the URL).

    entry is a name and a URL, not a java.io.File -- no canonical path, cannot
    be renamed in place, must never reach a local delete. Sharing the row would
    invite exactly that.

    THIS IS THE ONE PLACE ANDROID KEEPS ITS OWN IMPLEMENTATION ON PURPOSE, and
    it is worth understanding why before "unifying" it. DownloadManager is a
    SYSTEM SERVICE: the transfer continues after Prism is killed, survives a
    reboot, and handles connectivity changes. None of that is reimplementable
    inside an app process, and model files run to several gigabytes on a device
    whose OS kills backgrounded apps aggressively.

    JvmDownloader does not pretend to any of it. What it does instead is
    RESUME: the .part file is kept and continued with a Range request, so a
    download interrupted by quitting Prism restarts where it stopped. A server
    that ignores the range header answers 200 rather than 206, which is
    detected -- appending a full response onto a partial file would produce a
    corrupt archive of exactly the right size.

    The finished file is moved into place only on success. A truncated .gguf
    does not fail to load; it loads and generates nonsense.

    DONE 2026-08-04. me.friwi:jcefmaven:127.3.1, plus the jogamp Maven repo in
    settings.gradle.kts (jcef-api depends on JOGL, which is not on Maven
    Central). desktop/.../browser/CefRuntime.kt owns the lifecycle.

    NOT VENDORED. jcefmaven downloads and unpacks the native bundle for the
    host platform on first run into dataDir/jcef, rather than three platforms'
    binaries living in the repo. The cost is a visible first-run wait, which is
    why CefRuntime.state reports the phase and percentage and the page shows
    both -- hiding a 100 MB download behind a spinner makes the browser look
    broken the first time anyone opens it.

    CEF IS PROCESS-WIDE: one CefApp, many CefBrowsers. dispose() matters --
    leaking it leaves orphaned Chromium subprocesses after Prism exits, which
    on Windows reads as the app not closing.

    Embedded via Compose's SwingPanel around the browser's AWT component, keyed
    on tab id: re-parenting a live CefBrowser crashes CEF, so switching tabs
    swaps the component instead.

    platforms; desktop/.../ui/BlocklistPage.kt is the editor -- merged list,

    THE MERGED LIST IS PAGED, not rendered whole. It is hundreds of thousands
    of entries after the StevenBlack download; a LazyColumn over that is fine,
    but building the sorted List<String> behind it on the main thread is not,
    so the snapshot is taken on IO and shown 300 at a time.

    Removing a BUILT-IN entry cannot delete it from a file that gets refetched,
    so HostBlocklist whitelists it instead. The UI says which of the two
    happened -- otherwise "I removed it and it came back" is a mystery.

    The seed list moved from assets/mini_blocklist.txt to a SEED_HOSTS constant.
    A desktop JVM has no assets directory, and shipping a ten-line text file as
    a resource only to parse it back out is more moving parts than the data
    deserves. It also means blocking works before the StevenBlack download
    finishes and on a machine with no network.

    Blocking is applied in PRIVATE TABS ONLY, which is the Android behaviour
    and is preserved rather than "improved" -- changing it would silently alter
    what public browsing does.

    Source: PrismWebViewClient (170), private-by-default setting,
            biometric lock (androidx.biometric)
    Desktop: Windows Hello / polkit, or a password fallback.
    Done when: private tabs open and can be locked.

    MOSTLY DONE 2026-08-04. Private tabs open, are a separate category, respect
    private-by-default, and lock behind a passphrase (the plan's own "password
    fallback" -- Windows Hello needs WinRT and Linux has no common biometric
    API). When locked, titles and URLs are withheld too, not just previews: a
    locked tab whose title reads "Bank of ..." has not been protected.

    STRICTER THAN ANDROID in one respect. Each private tab gets its OWN
    CefClient, so Chromium isolates its cookies, storage and cache in an
    off-the-record context that dies with the tab -- two private tabs cannot
    even see each other's session. Android's WebView incognito shares a cookie
    manager and only disables third-party cookies per view.

    NOT DONE, AND THIS IS THE ONE THAT MATTERS: private tabs do not use the P2P
    VPN. On Android, selecting one starts PrivateDnsVpnService, a real system
    VPN. Desktop needs WinTun / CAP_NET_ADMIN (PHASE 47-49).

    The per-tab decision tree IS ported, in browser/VpnBridge.kt, including the
    "only act when the wanted state actually changes" guard that stops a tab
    switch from tearing the tunnel down and rebuilding it. It returns a
    Decision and logs; it does not pretend. Deliberate: telling a user their
    traffic is routed over the mesh when it is going out over their ordinary
    connection is worse than saying it is not. What private tabs DO get on
    desktop -- cookie isolation, ad blocking, DNT/Sec-GPC -- is real.
